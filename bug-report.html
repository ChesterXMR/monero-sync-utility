Incident Report / Monero Sync Utility / 28–30 Aug 2026

The daemon that would not die

Thirteen scheduled runs over three days. Two crashed the supervisor and left monerod running unsupervised — one of them for five and a half hours, blocking three subsequent runs and ending in the exact abrupt termination this utility was built to prevent.

What the logs actually show

The sync logic itself is sound. Every run that completed did so correctly: preflight checks caught what they were meant to catch, the peer guard held, and eight runs shut down with all four daemon farewell markers present. The database is intact at height 3,751,103.

The failures are all in the supervisor — the PowerShell script that babysits the daemon. Twice it died mid-run while monerod was still running, and because nothing else was watching, the daemon simply kept going with no one left to shut it down gracefully.

Finding 1 — the orphan

Critical Data-loss risk 29 Aug 15:34 → 21:08

Supervisor died mid-sync, orphaning the daemon for 5.5 hours

The 15:34 run passed all checks, started monerod as PID 26584, waited 577 seconds for RPC, and began polling. Then its log simply stops mid-poll — no shutdown step, no summary, no error. There is no entry in sync-history.log for this run at all, which means the script never reached its own summary code.

Finding 2 — the blockade

High Availability 29 Aug 17:57, 18:10, 21:10

The safety check became a denial of service

With PID 26584 still holding port 18081, the next three scheduled runs all hit check 3 and exited immediately — correctly, by design. But the design has no escape hatch: nothing detects that the running daemon is an orphan from a dead run rather than a live sync.

Finding 3 — the first crash

Critical Fixed 28 Aug 15:02

Blocking RPC client hung the supervisor indefinitely

The earlier failure had a different and now-understood cause. The shutdown step spawned monerod.exe ... exit as an RPC client, and that call has no timeout. Against a busy daemon it was measured blocking for 126 seconds; in this case it never returned at all, freezing the script on that line while the daemon ran on for 24 more minutes.

That daemon did eventually shut down cleanly on its own. This one has been fixed — the utility now sends POST /stop_daemon with a hard 60-second timeout, which returned in 15.2s where the client took 126s.

The database survived — this time

Worth stating plainly: there is no corruption. The 30 August run opened the 279.6 GB LMDB without complaint, synced 387 blocks, and closed cleanly. LMDB's copy-on-write design is genuinely resilient to a process being killed between transactions.

But that is luck, not protection. A kill that lands during a write is a different outcome, and the whole reason for the graceful-shutdown machinery is that you have hit corruption before. An orphaned daemon running unsupervised for five hours is exposure that the design is supposed to eliminate.

Fixes

Shipped
Non-blocking shutdown via stop_daemon
Replaced the timeout-less CLI client with an HTTP POST carrying a hard 60s limit. Verified at 15.2s against a busy daemon where the client took 126s. This addresses Finding 3 directly.
Shipped
Shutdown-marker verification
Every run now confirms the four exact farewell markers after exit. This is what made Finding 1 provable at all — without it, an orphaned daemon and a clean one look identical in the history.
Recommended
Adopt orphaned daemons instead of skipping
The highest-value remaining fix. When check 3 finds a running monerod with no live supervisor, the run should adopt and gracefully stop it rather than skip. That single change turns Finding 2 from a 5.5-hour blockade into a 3-minute self-repair.
Recommended
Shut the daemon down when the supervisor dies
Register a finally / ProcessExit handler so an unexpected script death still triggers a graceful stop. This is the root cause of Finding 1 — without it, any crash leaves a daemon running.
Recommended
Find out why the supervisor died
Still unexplained. The task's 3-hour limit was not reached and the last result was 0. Candidates: the machine going to battery (the task is set to stop on battery, which terminates the process without running cleanup), a logoff, or an unhandled error before the catch could log it. Worth enabling Task Scheduler's operational history to catch the next one.
